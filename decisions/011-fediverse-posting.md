# ADR-011: Posting to the fediverse through a member's linked account

- **Date:** 2026-10-26
- **Status:** Accepted (Adam, 2026-10-27, #66; his answers are in `DECISIONS.md`)
- **Scope:** posting, replying, boosting, favouriting, following and deleting on the fediverse from the River (`docs/spec/fediverse-posting-1.md`, `src/river/acting/fediverse/`), the linked-account screens, and the outbound requests they make. Not reading: the fediverse adapter (spec 4.3) is unchanged.
- **Extends:** ADR-010 (acting for members), ADR-001 (fetch guard; amends its list of allowed requests and adds `DELETE` to the guard's methods).

## Context

Spec 5 kept posting out of v1, with "a setting that links a person's Mastodon account so replies from the River come from that account" as the later idea, and kept "a River ActivityPub actor, inbox, push delivery or HTTP signatures" out too. The Phase 2 architecture notes chose no actor for v1 because "Fedify's queue wants a long-running worker, which Vercel serverless lacks" (`docs/design/architecture.md` A3). Adam asked (2026-10-26) for three approaches compared, with costs and risks, and one recommended:

1. Link an existing Mastodon-compatible account (Mastodon, GoToSocial, Akkoma) through its client API.
2. The River as its own ActivityPub server, each member an actor such as `@name@river.mosaic.social` tied to their Mosaic ID, built with Fedify.
3. Mosaic hosts GoToSocial, the River is its client, and people sign in to it with Mosaic ID through OIDC.

The River runs as Vercel functions (60 s maximum, no long-running process), on one free Supabase project reached through the transaction pooler (no `LISTEN`, no session advisory locks, no prepared statements), with a daily SQL-only `pg_cron` job. Every outbound request goes through the fetch guard. The River holds no member's private key (constraint 7). Today one person (Adam) is a member, and the Foundation has no moderation staff.

API details below were checked on 2026-10-26 against the sources themselves, read as raw files because the docs sites were unreachable from the build environment: Mastodon's documentation and source (`mastodon/documentation`, `mastodon/mastodon` on GitHub; latest stable 4.7.3), GoToSocial v0.20.3's source (from the Go module proxy; newer releases up to v0.22.3 exist and weren't read), Fedify 2.4.5's docs and source (`fedify-dev/fedify` at tag 2.4.5), and the FEP texts from a GitHub mirror of `codeberg.org/fediverse/fep` (not compared with Codeberg). Akkoma's docs couldn't be reached at all.

## Decision

**Approach 1: link the member's existing account and act through its client API.** The River is a client app of the member's own server, like a phone app. Their server keeps hosting their posts, followers and moderation; the River only sends what the member clicks.

1. **Which servers.** v1 links accounts on servers whose NodeInfo `software.name` is `mastodon` (4.3 or later, for PKCE, the `profile` scope and the discovery document, all new in 4.3) or `gotosocial` (0.19 or later, for scoped tokens). Akkoma and others are refused ("The River can't post through {software} yet") until a fixture check shows their API matches; Akkoma's docs couldn't be read for this ADR.
2. **App registration, once per server and River instance.** `POST /api/v1/apps` with `client_name: "Mosaic River"`, `redirect_uris: ["https://river.mosaic.social/api/auth/fediverse/callback"]`, `scopes`, `website`. The `client_id` and `client_secret` are stored in `river.oauth_clients` (the secret encrypted, ADR-010 §5) and reused for every member on that server. Mastodon throttles registration to 5 per 10 minutes per IP, and Vercel's addresses are shared, so a 429 here says "example.social is busy; try again in a few minutes".
3. **OAuth with PKCE.** Authorization code with `state` and PKCE S256, always (Mastodon's `/.well-known/oauth-authorization-server` must list it; GoToSocial supports S256 and has no such document). Scopes: `profile` on Mastodon, `read:accounts` on GoToSocial, `write:statuses`, `write:favourites`, `write:follows`, `read:follows`, `read:search`. No `read` or `write` umbrella scopes, no `write:media` in v1, never `admin:*`. Tokens don't expire and there are no refresh tokens (Mastodon and GoToSocial); any 401 means "link again" (Mastodon answers `The access token was revoked`, later `The access token is invalid`); a 403 means a missing scope.
4. **Acts** (each an ADR-010 act; the endpoints in the spec): post and reply (`POST /api/v1/statuses` with `status`, `spoiler_text`, `visibility`, `in_reply_to_id`, `language`, and an `Idempotency-Key`, which Mastodon keeps for an hour per account); boost and unboost; favourite and unfavourite; follow and unfollow; delete a post made from the River (`DELETE /api/v1/statuses/:id`). A River item becomes the member's server's local id through `GET /api/v2/search?q={object URI}&resolve=true&type=statuses&limit=1` (accounts the same way, `type=accounts`), which makes their server fetch it.
5. **In v1 and not:** text, content warnings, and the visibilities Public, Quiet public and Followers only. Out: media (spec item 6 says why), direct messages, polls, quote posts, edits, scheduled posts, reading notifications.
6. **Allowed requests, added to ADR-001's list.** To the host that serves a member's fediverse account (the host of the actor URL their handle resolves to through WebFinger, which can differ from the handle's domain), only for a member who asked to link it or has linked it: `GET /.well-known/nodeinfo` and its NodeInfo document, `GET /.well-known/oauth-authorization-server`, `GET /api/v2/instance`, `POST /api/v1/apps`, `POST /oauth/token`, `POST /oauth/revoke`, `GET /api/v1/accounts/verify_credentials`, `GET /api/v2/search`, `POST /api/v1/statuses`, `DELETE /api/v1/statuses/:id`, `POST /api/v1/statuses/:id/{reblog,unreblog,favourite,unfavourite}`, `POST /api/v1/accounts/:id/{follow,unfollow}`, `GET /api/v1/accounts/relationships`. WebFinger for the handle is already allowed (ADR-001 item 1). Every request goes through the guard unchanged (HTTPS, address checks, 6 s, 2 MB, 2 per host, `Retry-After`). Every request that carries a token or a client secret is made with **redirects off** (`maxRedirects: 0`), so a credential is never sent to a host it wasn't issued for. The browser goes to the server's `/oauth/authorize` page itself (a navigation, not a River request).
7. **A guard change:** `DELETE` joins `GET`, `HEAD` and `POST` in the guard's methods (for deleting a post). Nothing else in the guard changes. It is a fetch guard change, so `needs-adam`.
8. **Credentials** follow ADR-010 §5 and §6: tokens and client secrets are encrypted with `RIVER_TOKEN_KEY`, never reach the browser, and are revoked (`POST /oauth/revoke`) on unlink.

**If Mosaic later hosts fediverse accounts** (approach 2 or 3), linking an existing account stays offered: people who already have a fediverse identity, followers and a home server keep them, and the River's client code is the same code approach 3 would use.

## Alternatives considered

### Approach 2: the River as its own ActivityPub server, built with Fedify

Each member would be an actor (`https://river.mosaic.social/users/{name}`, handle `@name@river.mosaic.social`) with an inbox, an outbox, followers and following, tied to their Mosaic ID. Fedify 2.4.5 (MIT, Node 22+) provides the federation layer, with `@fedify/express` mounting it (`app.use(integrateFederation(federation, …))`).

**Delivery, the inbox and retries on Vercel and Supabase.** Federation needs a queue: Fedify sends and processes activities through a `MessageQueue`, retries failed deliveries (default `createExponentialBackoffPolicy`: 10 attempts, delays from 1 s doubling to at most 12 h, 404 and 410 counted as permanent), and fans out to many inboxes through a separate fanout queue (`fanout: "auto"` above 5 inboxes). Without a queue, `sendActivity` sends once with no retry, and Fedify's docs call immediate sending "actively dangerous in production". The options:

- **Fedify's `PostgresMessageQueue`** (`@fedify/postgres`) polls a table every 5 s and uses `LISTEN`/`NOTIFY` and session advisory locks; Supabase's transaction pooler supports neither, so it needs a direct or session-mode connection and a long-running consumer. It also uses the `postgres` driver, not `pg`, which constraint 2 forbids outside `src/db/`. Not workable on Vercel functions.
- **A push queue driving `manuallyStartQueue` and `processQueuedTask()`**, the pattern Fedify documents for Cloudflare Workers and Netlify Functions (2.4.0+): on Vercel this needs an outside queue service that calls a function (Upstash QStash, or Vercel's own queue product; neither's free allowance or fit was checked). A new paid or outside service: `needs-adam`, and Fedify has no Vercel adapter, so we'd write and maintain one.
- **A Postgres outbox table drained by something:** `pg_cron` may make no network calls (spec 4.5; `pg_net` would break that rule), Vercel Hobby crons run at most daily, and draining on page loads under `waitUntil` stalls whenever nobody visits, which a retry schedule reaching 12 h can't live with.
- **A small always-on worker** (a VPS or a container host) running Fedify with `PostgresMessageQueue` over a direct connection: works, but it's a third deployable and a paid service.

The inbox itself can be a function (each delivery is one POST), and Fedify verifies incoming signatures, but verifying means fetching each sender's actor (outbound to any host, through the guard), and processing must be queued, so it hits the same wall.

**Signatures and keys.** Mastodon requires HTTP Signatures (draft-cavage, RSA-SHA256, signing `(request-target) host date digest`, `Digest` required on POST, requests over 12 hours old refused); it checks RFC 9421 by default since 4.5 and adds Ed25519 in 4.7. Fedify signs both with "double-knocking" and adds FEP-8b32 object proofs with Ed25519, but its HTTP and Linked Data signatures are RSA only. So the River would hold an RSA private key (and an Ed25519 one) per actor. Constraint 7 says the River never holds private keys; keeping them at Mosaic ID instead would mean one identity-host signature per delivery, for every follower's inbox. Either the constraint changes or the actor server becomes a separate app.

**Followers, following, replies and notifications.** A Follow from any server becomes a follower row and an Accept (or a request, for a locked account); following others sends Follow and waits for Accept; their posts then arrive in the member's inbox, per member, which is a different storage model from the River's shared public items (ADR-003 reserved `items.account_id` for this). Replies and mentions need a notifications table and screen, and followers-only posts need audience checks on every read. Mastodon also expects `featured`, `alsoKnownAs` and a WebFinger round trip on `preferredUsername` from actors.

**Deletes, blocks, spam, moderation and reports.** Incoming `Delete` must remove stored copies (and Tombstones answer 410 for our deleted actors and posts; Fedify serves a returned `Tombstone` as 410 on both the actor and WebFinger). Members need block and mute (a `Block` sent to the other server), and the instance needs server-level domain blocks applied to both delivery and the inbox, probably seeded from a shared blocklist. Mention spam arrives in waves across the fediverse, so the inbox needs per-server limits and a hold for unknown senders. Incoming `Flag` reports need a moderation queue and someone to work it; members need a way to report posts to other servers. Fedify supplies the activity types; every behaviour is ours to build.

**Terms and legal duties of hosting posts.** Hosting people's posts makes Mosaic a hosting provider. What follows was not checked against primary sources this session and is a list for counsel, not advice: terms of service and a privacy policy; a minimum age; in the US, a DMCA designated agent (registered with the Copyright Office) and a repeat-infringer policy for the safe harbour, and reporting apparent child sexual abuse material to NCMEC once known; in the EU, the Digital Services Act's hosting duties (notice and action, statements of reasons, a point of contact, and a legal representative for a provider outside the EU that serves EU users); in the UK, the Online Safety Act's risk assessments for user-to-user services with UK users; GDPR for EU members' data. To be listed by joinmastodon.org a server must also commit to the Mastodon Server Covenant: active moderation, daily backups, a second person with emergency access, and three months' notice before shutting down (`joinmastodon` repo, `pages/covenant.tsx`).

**Usernames.** A handle needs a chosen username, which the River doesn't have (Mosaic IDs use random codes and display names, architecture Q3): uniqueness, reserved names, squatting and renames (a rename is effectively a Move).

**Custom domains later.** A member's own domain as handle (`@ana@ana.example`) works by serving WebFinger on that domain pointing at the River's actor. Fedify supports one handle host separate from its web origin (`origin: { handleHost, webOrigin }`), and several through virtual hosting (`Context.host`, without `origin`).

**Account Move.** Out of the River: set `movedTo` and send `Move` to followers; Mastodon re-fetches the target and requires its `alsoKnownAs` to list the old actor, then moves followers (posts don't move; 30-day cooldown on Mastodon, 7 on GoToSocial). Into the River: the River actor lists the old actor in `alsoKnownAs` and accepts the Follows that arrive. Fedify has the vocabulary (`getSuccessor()`, `getAliases()`) but no migration workflow; FEP-7628 (pull and push Move) is a draft Fedify doesn't list.

**Linking the actor to the member's DID.**
- **FEP-c390 identity proofs** (draft): a `VerifiableIdentityStatement` with `subject` the member's DID and `alsoKnownAs` the actor id, signed (`eddsa-jcs-2022`) by the DID's key, placed in the actor's `attachment`. It names no required DID method, so a `did:webvh` works, and Mosaic ID could sign the statement with the key under `assertionMethod` (ADR-012). Mitra, Streams and Forte implement it; Fedify doesn't, so we'd write the JCS proof ourselves. The DID document's `alsoKnownAs` would list the actor back.
- **FEP-ef61 portable objects** (draft): object ids like `ap://did:key:…/…` served through gateways, every object carrying an FEP-8b32 proof from the same DID. It requires `did:key` and says other methods "SHOULD NOT be used" (`did:webvh` is "being considered"). Fedify 2.4 supports it for `did:key` Ed25519 only. Mosaic's `did:webvh` DIDs can't be the authority today; a `did:key` per member would be another private key someone holds. Worth tracking, not adopting.

**Should following as a real server replace polling for reading?** Not now. Push would reach servers that only share with other servers (today's `blocked` spaces, spec 4.3) and cut requests, but it needs the always-on inbox and queue above, per-member subscriptions (or one instance actor following on everyone's behalf), and polling would stay as the fallback anyway. A cheaper step, if `blocked` spaces matter: an instance actor that only signs GET requests (a server key, no inbox, no queue). That would be its own ADR.

**Costs and risks, in short:** the largest build of the three (the actor server, queue, inbox, moderation tools, notifications), a paid always-on component or an unchecked outside queue, a constraint 7 change, usernames, and Mosaic becoming a host with moderation and legal duties. It is also the only approach that gives every member a fediverse identity tied to their Mosaic ID.

### Approach 3: Mosaic hosts GoToSocial, signed in with Mosaic ID

GoToSocial (AGPL-3.0, beta, "intend to exit beta some time around 2026") is one Go binary or container with SQLite or Postgres; its docs ask for a server with 1 core, about 1 GB of RAM (250 to 350 MB typical) and 15 to 20 GB of storage, plus somewhere for media. It implements most of Mastodon's client API, so the River's client is approach 1's code with the server preset. It brings domain blocks (blocklist by default; an "experimental" allowlist mode), reports (sent as `Flag` from its instance actor), aliases and Move, and a 5,000-character default limit.

**What Mosaic ID would need, as an OIDC provider:** a discovery document (`/.well-known/openid-configuration`), an authorization endpoint (code flow, PKCE), a token endpoint, ID tokens signed with a published key (`jwks_uri`; which algorithms GoToSocial's OIDC library accepts wasn't checked, and if it's RS256 only, Mosaic ID would need an RSA signing key of its own), a userinfo endpoint, and the claims GoToSocial reads: `sub` (stable; the SCID), `email` and optionally `preferred_username`. GoToSocial refuses a new user unless the provider sends a non-empty, unique `email` claim (`openid` and `email` are required scopes); `email_verified` isn't required. So Mosaic ID would hand GoToSocial each person's email address, or a unique stand-in address per person (that a stand-in passes is an inference from GoToSocial's code, not documented). Mosaic ID would also need GoToSocial registered as a client and a consent screen for it.

**Costs and risks:** a paid server (`needs-adam`), operating it (updates, backups, uptime, media storage), the same hosting, moderation and legal duties as approach 2, people's email addresses (or stand-ins) leaving Mosaic ID, and dependence on beta software. Less to build than approach 2, since GoToSocial does federation, queues and moderation tools.

### Approach 1's own costs and risks (the recommendation)

Smallest build (five or six PRs: HANDOFF.md's A1 to A5, with the guard change as its own PR), nothing new to host, no queue, no new private keys, and no hosting duties: the member's server hosts their posts under its own rules. It works within Vercel's request model because every act is one or two requests in the click. It only helps members who already have a fediverse account; the River holds tokens that can post as them (bounded by ADR-010's encryption, limits, audit list and revocation); behaviour differs a little between Mastodon and GoToSocial (character counting, idempotency, which GoToSocial version supports what); and per-server app registration is rate-limited from Vercel's shared addresses.

## Consequences

- Members with a Mastodon or GoToSocial account can reply, boost, favourite, follow and post from the River, as themselves.
- Members without one can't post to the fediverse from the River. Mosaic doesn't host fediverse accounts for now; approach 2 (the River as its own ActivityPub server) is recorded as the long-term option to revisit (Adam, 2026-10-27; `DECISIONS.md` later options).
- New outbound requests to members' own servers (Decision 6), a guard method (`DELETE`), new tables (ADR-010) and the River secret `RIVER_TOKEN_KEY`: all `needs-adam`.
- Fixtures: synthetic ones built from Mastodon's documented shapes and a stand-in server for tests; real recordings need a test account on a real server, which only Adam can create.
- Revisit when Akkoma is checked, when media is wanted (an upload path within Vercel's request limits), and if Mosaic decides to host accounts.
