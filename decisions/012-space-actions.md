# ADR-012: Space actions, signed as the member's DID

- **Date:** 2026-10-26
- **Status:** Proposed
- **Scope:** the Mosaic Space Actions protocol (`docs/spec/space-actions-1.md`): how a space advertises actions, what Mosaic ID signs, how a space verifies it; Mosaic ID's grant and signing endpoints; the River's action buttons, composer and delivery (`src/river/acting/spaces/`); the shared reference code (`src/shared/spaceActions/`); the outbound requests all of these make.
- **Extends:** ADR-010 (acting for members), ADR-001 (fetch guard; amends its list of allowed requests), ADR-003 (item model). **Changes ADR-002** (identity host and sign-in) as listed in Decision 6.

## Context

A Civic Hub already tells callers what a resident may do: its process descriptor lists `actions` with input schemas and an `endpoints.action` URL (`civic-hub/src/services/processDescriptor.ts:90-157`), and `civic.json` lists each process type's actions. Its comments, supports and ballots are reached through `POST /process/:id/input`, `POST|DELETE /proposals/:id/support` and `POST /process/:id/action`, each behind a bearer-token session minted by the hub's own email-code sign-in (`civic-hub/src/middleware/auth.ts`), and each needing a self-affirmed resident with a real name (`src/authz/eligibility.ts`). The hub reserves `users.identity_did` for DID sign-in and serves `did:web:{host}` as its space id, with no keys yet.

Adam's plan (2026-10-26): a space says in its feed which actions an item accepts (comment, support, RSVP, poll answer); the River shows them; the action reaches the space signed as the member's DID by Mosaic ID; the space verifies it the way the River verifies sign-in notes. It must be a small open protocol any Mosaic space can implement, testable by a conformance suite.

Today the River and Mosaic ID meet only through the sign-in redirect and the signed note (ADR-002), Mosaic ID keeps no session and signs only sign-in notes, and the River holds no keys (constraint 7).

## Decision

1. **A protocol of its own, "Mosaic Space Actions 0.1"**, specified in `docs/spec/space-actions-1.md`, with four parties: the member, a client (the River), a signer (Mosaic ID) and a space (a Civic Hub or any Mosaic space).
2. **Advertising in two places.** The space's manifest (`/.well-known/civic.json` for Civic.Social spaces) names the protocol version, one action endpoint on the space's own host, the audience to sign for (its `space.id`), the DID hosts it trusts, the verbs it accepts, and where to join. Each feed activity whose object accepts actions carries `civic:actions`, a short public list: verb, target IRI and a few parameters (length limit, RSVP options, poll choices, closing time, whether a passkey is needed). No per-person state is ever in the feed.
3. **Four verbs and a withdraw:** `comment` (plain text), `support`, `rsvp` (`yes`, `no`, `maybe`), `poll_answer` (choice ids), and `withdraw` (of an earlier action, by the id the space returned). The spec maps each to the AS2 activity a space would publish (Create Note, Like, Accept/TentativeAccept/Reject, Create Note with `name` on a Question, Undo). **Secret ballots are excluded:** a signed action names its signer, so a space must never advertise a verb for a vote whose ballots are secret.
4. **The request is a compact JWS** (`typ: "mosaic-action+jwt"`, `alg: EdDSA`, `kid: {did}#key-1`), sent as the whole body of `POST {endpoint}` with `Content-Type: application/jwt`. Its claims: `iss` and `sub` (the member's DID), `aud` (the space's id), `htm` and `htu` (the method and exact endpoint URL), `iat` and `exp` (at most 300 s apart; Mosaic ID uses 120), `jti` (replay), `client` (the client's origin, set by Mosaic ID from the authenticated client), `assurance` (`grant` or `passkey`), optional `name` (the Mosaic ID's display name), and `act` (the verb, target, content or choice, and `ref`, the client's idempotency key, stable across retries). The space answers with JSON (`accepted` with the new object's id and link, or `held` for review) or a problem document with one of a fixed list of codes.
5. **The space verifies it like the River verifies a sign-in note** (spec 4.6 step 4): `typ` and `alg` fixed, `kid` under `iss`, the DID's host on the space's trusted list before any request, `aud` and `htu` exact, times with 60 s leeway, the DID log resolved through the space's own fetch guard and verified, the signature checked with a key the current DID document lists under **`assertionMethod`** (not `authentication`: an action is a statement, a sign-in is a proof of control). Then `ref` (idempotency, 24 hours) and `jti` (replay, until `exp` plus leeway), then the action against the target's current state, then the space's own membership, moderation and limits. The steps are numbered in the spec so a conformance suite can test each one.
6. **What Mosaic ID needs, and what changes in ADR-002.**
   - **A grant, consented once with a passkey.** The River sends the member to `https://id.mosaic.social/grant` (an OAuth 2.1-shaped authorization request: `client_id`, exact `redirect_uri`, `state`, PKCE `S256`, `scope` such as `space-actions:comment space-actions:support`). Mosaic ID shows in plain words what the River will be able to send as the member, runs a passkey check, and redirects back with a one-use, 60-second code. The River exchanges it server to server at `POST /grant/token` for a grant token, which it stores encrypted (ADR-010 §5); Mosaic ID stores only the token's SHA-256, with the client, person, scopes, and created and last-used times.
   - **A signing endpoint.** `POST https://id.mosaic.social/actions/sign` (client-authenticated; body: grant token, `aud`, `htu`, `act`) checks the grant and its scope, checks `act` against the same schema spaces use, applies per-person limits (60 an hour, 300 a day), adds `iss`, `sub`, `iat`, `exp`, `jti`, `client`, `assurance: "grant"` and `name`, signs with the person's custodial key, writes `audit_log` (`action_signed`: client, `aud`'s host, verb, `jti`, never the content), and returns the JWS. Mosaic ID makes no outbound request: it never contacts the space.
   - **Step-up, per action, for a target marked `assurance: "passkey"`:** the River pushes the request (`POST /actions/requests`, like OAuth PAR) and sends the member to `GET /actions/confirm`, where Mosaic ID shows the action itself and runs a passkey check, then redirects back with a code the River exchanges at `POST /actions/token` for a JWS with `assurance: "passkey"`.
   - **Revocation:** `POST /grant/revoke`, and a list with Revoke buttons on Mosaic ID's account page. A recovery revokes all of a person's grants (ADR-010 §6).
   - **Client authentication:** each registered client gets a secret; the River holds it as `MOSAIC_ID_CLIENT_SECRET`, Mosaic ID holds only its SHA-256 in `IDENTITY_CLIENT_SECRET_HASHES` (origin and hash pairs). A secret, not a key pair, so no private key is added to either side.
   - **DID documents gain `assertionMethod: ["#key-1"]`**, the same custodial key. Mosaic ID appends the log entry the first time a person grants, and `recover-dids` keeps `assertionMethod` when it re-keys.
   - **ADR-002, before and after.** Before: the two apps meet only through the sign-in redirect and the signed note. After: they also meet through the grant redirect (the same shape as sign-in: state cookie, exact redirect URI) and through four server-to-server HTTPS calls from the River to Mosaic ID (`/grant/token`, `/actions/sign`, `/actions/requests` with `/actions/token`, `/grant/revoke`), client-authenticated. Mosaic ID now holds per-client state (grants) and signs a second kind of JWS. Unchanged: no identity-host session, no email or key ever reaches the River, River code and identity code still never import each other, and the sign-in note is as it was. These endpoints are deliberately shaped like OAuth 2.1 (authorization code, PKCE, pushed requests) so the atproto-style OAuth profile ADR-002 plans can absorb them: DPoP-bound tokens would then replace the client secret.
7. **The River's part.** It reads `civic:actions` from feeds and `actions` from manifests (stored in a new `river.items.actions` column and in `spaces.manifest`), shows the verbs it knows on live cards whose space advertises a matching endpoint, asks for the grant on first use, previews and records each action (ADR-010), asks Mosaic ID to sign it, posts the JWS to the space, and shows the answer. Text actions (comment, poll answer) are previewed; support and RSVP are toggles. "Not a member yet" answers link to the space's join page, opened as a full page (`docs/civic-hub-changes.md`).
8. **Allowed requests, added to ADR-001's list.** Every one through the fetch guard unchanged (HTTPS, address checks, 6 s, 2 MB, 2 per host, `Retry-After`), with redirects off (a guard created with `maxRedirects: 0`, so a 3xx is a failure and nothing is re-sent elsewhere):
   - **River → Mosaic ID** (`IDENTITY_ORIGIN`'s host, already reached for DID logs): `POST /grant/token`, `POST /actions/sign`, `POST /actions/requests`, `POST /actions/token`, `POST /grant/revoke`. Locally, the identity dev server on loopback through `src/shared/fetch/loopback.ts`'s rules, extended to these paths (test-only, `TEST_DID_LOOPBACK`).
   - **River → a space:** `POST` of a signed action to the `actions.endpoint` of a space the member follows (or whose item is in their River), only when that endpoint is https on the same host as the space's manifest, body at most 16 KB, no cookies, no `Authorization` header. A manifest that names another host is ignored (no actions shown).
   - **Mosaic ID:** none.
   - **Spaces** resolve members' DID logs at `id.mosaic.social`; that is the space's own outbound request, under its own rules (the Civic Hub's are in `docs/civic-hub-changes.md`).
9. **Testing without real hubs.** The protocol's reference verifier lives in `src/shared/spaceActions/` (pure, with an injected DID resolver), and a stand-in space built on it serves a manifest, a feed and an endpoint. Unit and API tests reach it through the guard's injected dispatcher, never the network; signed test vectors (a fixed test DID log and key, a valid request and one per refusal) make the conformance suite any space can run.

## Alternatives considered

- **The River holds a delegated key per member** (Mosaic ID signs a capability once; the River signs each action): no call to Mosaic ID per action, but the River would hold private keys (constraint 7), and spaces would have to verify delegation chains and their revocation.
- **A passkey check for every action:** strongest consent, but a support click would become a page change and a fingerprint; kept as step-up where a space asks for it.
- **Mosaic ID delivers the action to the space:** Mosaic ID would make outbound requests to arbitrary hosts from the host that holds every key; the River already has the guard and the error handling.
- **ActivityPub delivery with HTTP Signatures from a DID-backed actor:** the member has no ActivityPub actor (ADR-011 doesn't build one), and HTTP Signatures sign the transport, not the statement, so a space couldn't keep a verifiable record of who said what.
- **A Verifiable Credential or Data Integrity proof (`eddsa-jcs-2022`) on an AS2 activity:** standards-aligned and a good later step (it matches FEP-8b32 on the fediverse), but needs JSON canonicalization on both sides; a JWS reuses the sign-in note's verifier, which spaces implementing "Sign in with Mosaic ID" will already have.
- **The space reads the action from the River (pull):** the space would have to reach every client, and replay windows get longer.
- **Actions only in the manifest (no per-item list):** the River couldn't tell which items accept what without a request per item.
- **One grant per space:** more consent screens for little gain, since the River already shows each action before it is sent; instead the River notes the first action at each space ("demosville.civic.social will see your Mosaic ID and its name").
- **Verifying against `authentication`:** no DID log change, but it blurs a sign-in proof with a signed statement.

## Consequences

- Any Mosaic space can accept actions from River members without the River knowing anything about its internals, and a space can verify, keep and later prove who did what.
- Every action costs two outbound requests from the River (Mosaic ID, then the space) inside the member's click, plus the space's DID resolution (cached).
- The same DID goes to every space a member acts at, so spaces can link a member's actions across spaces. Pairwise DIDs would fix that and are out of scope.
- Mosaic ID becomes a signing service for registered clients. A compromised River could have Mosaic ID sign within each member's grant and limits, but not beyond: the grant scopes, Mosaic ID's limits, its audit log, and revoking all of the River's grants at once bound it.
- Schema: new identity tables (`grants`, `action_requests`), new `audit_log` action values (a CHECK change on an existing table), `river.items.actions` (new column), new River tables from ADR-010. All `needs-adam`.
- The Civic Hub needs its own changes before any of this works against a real hub (`docs/civic-hub-changes.md`).
